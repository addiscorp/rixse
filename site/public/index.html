Agentic UI. One state, two authors.

The user and the agent shape the same interface through the same typed actions. The agent describes what to show; the app renders it.

ui = agent(schema, view(state), prompt)

One real turn, step by step

01 · Prompt

“compare these over the years”

The user has selected two bars: Avatar (movie) and Titanic (movie). The selection is part of the input, so “these” has a referent.

02 · Schema

Components: stat, bar, pie, line, table, graph. Sizes: viewport → large → medium → small.

Movies data: title, year, gross, and cast, directors and genres relationships. The source tells the agent how to query it.

03 · view(state)

The current screen is a top-10 box-office bar chart. The agent sees the typed view state and the selected items, not pixels or chart markup.

top 10 by gross
04 · Agent

The agent outputs a typed action with a query and chart parameters:

view.show({
  id: 'gross-over-time', kind: 'line',
  title: 'Box office over time',
  query: '{ Movie(title = "Avatar" || title = "Titanic") limit 100000 { title year gross } }',
  label: 'title', x: 'year', value: 'gross', size: 'large'
})

About 92 output tokens for a full chart turn in the iOS log.

That is a small observed demo response; exact usage varies by model and prompt.

05 · State → UI

The action updates state. The source returns rows to the app, and view(state) renders the line chart. The same state and layout rules render deterministically on web and iPhone.

Why it matters

  • Typed and attributableThe agent can only use allowed actions. The log records who changed what.
  • Tiny outputsA few action fields specify a chart, keeping responses fast and inexpensive.
  • One state on every platformWeb and native Swift use the same state model and shared conformance vectors.
  • One shared interfaceThe user and agent both act on the same state through the same vocabulary.
